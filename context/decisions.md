### 2026-09-04 — Real mobile bug in the book scene, tighter outings gap, sitewide polka-dot texture
- **Real bug fixed: the book scene's video-left/copy-right flip never reset on mobile.** `#books .scene__content`/`#books .scene-copy`/`#books .scene-visual` are ID-scoped overrides, so they out-specificity the general mobile breakpoint's `.scene__content { grid-template-columns: 1fr }` reset — the 2-column desktop layout (and the order-swap putting video first) was silently surviving all the way down to phone widths, causing the cramped, text-truncated layout in the owner's screenshot. ### 2026-09-04 — Real desktop-layout alignment bug found in the milestone timeline; expanded card gets a background
- **Real bug, finally reproduced and fixed:** the previous session's alignment investigation (logged below) found nothing wrong because it was only tested at viewport widths under the `60rem` breakpoint, where the timeline uses its 2-column mobile layout. At full desktop width (3-column layout: `1fr 2.75rem 1fr`), every **left**-side item's label sat a fixed ~48px below its own marker, while right-side items were fine. Root cause: CSS Grid's sparse auto-placement algorithm advances a placement "cursor" left-to-right as items are placed; since the marker (`grid-column: 2`) is placed first in DOM order, the cursor moves past column 1 — so a later item explicitly requesting `grid-column: 1` (the left-side label) can't reuse that earlier column in row 1 and silently gets bumped into an implicit new row, while `grid-column: 3` (right-side) is still ahead of the cursor and stays in row 1. Fixed by adding `grid-row: 1` explicitly to the marker and both left/right label rules (including the mobile 2-column override, for safety) so placement no longer depends on DOM order vs. column direction. Lesson: verify layout bugs across the actual breakpoint that reproduces them, not just whichever width happens to be open.
- **Added a background card behind the expanded milestone's age/title/description** — the connecting vertical line was rendering visibly through the gaps of the text since that block had no opaque background, per the owner's own suggested fix. Used the standard `.card`-style treatment (paper background, ink border, flat shadow) already used everywhere else on the site, rather than inventing a new visual treatment.

### 2026-09-04 — Fixed faces getting cropped out of carousel photos
- **Root cause:** most source photos are portrait-orientation phone shots; forced into the carousel's 4:3 landscape box via `object-fit: cover` with the CSS default `object-position: center`, the crop symmetrically trims top and bottom — which, for a portrait photo, cuts a lot of height and often removed the top of the frame where faces usually are.

- **Verified against all 24 photos across all 5 locations** (Please Touch, Zoo, Aquarium, PG's, Mom Mom's) in-browser — the single top-biased default fixed every case; no per-photo `focus` overrides were needed this round. Left the override mechanism in place for future photos that might need it.
